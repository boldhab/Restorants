# Phase 2: restaurant publishing

## Run and demonstrate

Use Node 24 and the existing npm workspaces. Run `npm ci`, `npm run setup:dev`, start PostgreSQL with the existing development Compose file, then `npm run db:migrate`, optionally `npm run db:seed`, and `npm run dev`. Apply migration 003 before starting upgraded application code. The seed is development-only. Phase 1's Bella Italia and Tokyo Ramen accounts remain separate tenant fixtures.

Sign in as an existing verified owner, choose a restaurant, and open **Menu & website** (`/workspace/{restaurantId}/website`). The editor resumes the existing restaurant; it never creates another restaurant. Work through Profile, Hours, Images, Categories, Items and Website, saving each step. Completion is derived from validated saved content, with outstanding requirements on Publish. Upload a cover image with alternative text; choose it as Cover image. Create a visible category and an active item. Add a variant (replacement price) and modifier group (addition prices). Preview displays the **saved** draft with mobile, tablet and desktop widths. Save unsaved changes to include them in preview.

Publish, then visit `/r/{slug}` logged out. Menu, About, Gallery and Contact use the shared renderer. Empty/disabled optional pages return 404. Search, category navigation and the keyboard-accessible native dish dialog work without an account. Configuration validation uses the published revision and does not create an order. Edit a draft price and verify the public price stays unchanged; republish to switch it. Apply Sold out under Items to update operational availability without publishing. Unpublish to remove the public site and its image routes.

## Data and concurrency

Migration `003_phase2_publication.sql` adds versioned drafts, immutable publication revisions, the current publication pointer, tenant-scoped media, publication/asset references, category/item identity and price records, operational availability and price history. Related references use composite tenant foreign keys. Variants, modifier groups/options/assignments, opening hours/exceptions, controlled theme fields and sections live inside the validated draft aggregate rather than separate editable tables. This is an intentional modular-monolith aggregate: each save validates the entire menu and atomically writes identities, price history and the draft. Phase 3 can normalize configurations while retaining immutable revision payloads.

All Phase 2 mutations require an existing verified session, active membership, active/onboarding tenant and `restaurant:update`. Existing CSRF validation applies, including binary uploads. Staff without update permission cannot preview or edit. The backend checks image ownership on every save. Slugs retain Phase 1 immutability. Only the existing default branch is usable; hours and item availability apply to that branch, and no multi-branch controls are exposed.

Saves send an expected integer version. All writes lock the restaurant row; stale saves/publishes return 409. Phase 1 profile edits also lock this row, synchronize overlapping settings into the draft and increment its version. A save archives existing categories/items instead of deleting identity/history. Archiving a category hides its items on the next publish, with no implicit item deletion. Public content remains unchanged until publishing.

Publishing locks the same row, validates essentials and media, filters active categories/items, creates an immutable snapshot, records its media dependencies, switches the pointer and writes an audit event in one transaction. A unique restaurant/draft-version constraint makes repeated requests reuse the same revision. Failure rolls back the pointer change. Unpublish deletes only the pointer and records an audit event. Historical revisions are retained and cannot be updated/deleted through SQL triggers. Republishing the same saved version after unpublishing restores that revision.

## Hours and availability

Week arrays use Sunday = 0 through Saturday = 6. Each interval uses integer minutes from midnight. Equal endpoints are invalid; a closing minute earlier than opening denotes an overnight interval belonging to its starting day. Multiple intervals and closed days are supported. Weekly overlap, including next-day spillover, is rejected. Date exceptions have unique ISO calendar dates; an empty interval array means a temporary closure. An exception for the current local date suppresses previous-day overnight spillover. A previous-date exception may itself supply overnight hours if today has no exception. Evaluation uses IANA timezone date/hour parts; opening is inclusive and closing exclusive. DST evaluation follows the restaurant's actual local wall clock (repeated clock times are open on both occurrences).

Operational item state is separate from publication content. It includes enabled, sold out, service modes and an optional hours/exception schedule. Only published items appear publicly. Restaurant closed and item sold out are distinct; browsing continues while closed. The configuration endpoint can accept `?mode=dine_in|takeaway|delivery` and validates mode eligibility. Names, prices, images, variants/modifiers and archive state change only on publishing. Operational updates are immediate in API responses; open browser pages refresh them every 15 seconds. A publication change reloads the page. Existing configuration requests with an old revision return 409 and ask the visitor to refresh.

## Money

Prices are authoritative integer ISO 4217 minor units (100 = one USD/ETB/EUR, 1 = one JPY, 1000 = one KWD). Inputs never parse decimal amounts into binary fractions. The editor explicitly requests minor units. Formatting uses Intl currency precision. No rounding is required for authoritative menu arithmetic: variant prices replace the base; one selection of each modifier adds an integer amount. Group minimum must not exceed maximum, and maximum must fit the available options. Identifiers and options are unique. Unsupported currencies are rejected. A database trigger and draft service reject currency changes after any menu item exists, including archived items. Conversion needs an explicit future migration; changing a currency never silently relabels amounts. Taxes, fees and checkout are outside this phase.

## Media and retention

Uploads use raw `application/octet-stream` bytes plus `X-Image-Alt` (percent-encode Unicode text in this HTTP header). The browser reports upload progress and allows retry. The server limits input to 5 MiB, 6000px per side and 24 megapixels, checks decoded content, allows only static JPEG/PNG/WebP, and re-encodes to WebP with metadata removed. It ignores filenames and declared image MIME types. Server-generated UUID object keys never come from a request. No media record is committed until processing/storage succeed; a later transaction failure attempts object cleanup.

`MEDIA_STORAGE=local` stores files outside source/executable paths; use an isolated persistent `MEDIA_LOCAL_ROOT` volume in production. The default `/tmp/zayqora-media` is development-only ephemeral storage. `MEDIA_STORAGE=s3` uses a private S3-compatible bucket via HTTPS path-style AWS SigV4 requests. Configure `MEDIA_S3_ENDPOINT`, `MEDIA_S3_BUCKET`, `MEDIA_S3_REGION`, `MEDIA_S3_ACCESS_KEY`, `MEDIA_S3_SECRET_KEY`. This adapter supports static IAM/access keys, not temporary session credentials. Storage operations have a 30-second timeout and fail closed. No object URL or bucket key is sent to the browser. Production S3 interoperability requires checking against the chosen provider; no live provider is claimed verified here.

Media bytes are delivered only to a verified authorized member or through an active publication's asset dependency. Unpublished media are not exposed publicly even if a UUID is known. Deleting media referenced by a saved draft or any historical publication returns 409. Historical assets are retained indefinitely with revisions; this conservative retention prevents broken historical and active publications. Unattached draft assets may be explicitly deleted in the library. The local cleanup command documents and removes abandoned objects after a seven-day grace period; never apply a bucket lifecycle rule to live referenced objects. S3 orphan cleanup requires an operator inventory comparison with `media_assets.object_key`; automated remote inventory is not implemented.

## API and caching

See `openapi.json`; regenerate Phase 2 schemas/routes after building contracts with `node scripts/update-phase2-openapi.mjs`. The editor uses `GET/PATCH /restaurants/{id}/website/draft` for atomic multi-feature saves. Focused settings, category/item create/replace/reorder, theme and availability endpoints are also provided. Category/item replacement includes archive/visibility state, variants and modifiers. Lists support offset/limit; the full aggregate is bounded at 100 categories, 1000 items and a 1 MiB request ceiling. Publication status/history (latest 50) and media metadata are returned with the draft. Preview is a private saved-draft response. Uploads are synchronously finalized, with no signed-upload pending state.

All API responses, private images and published content carry `Cache-Control: no-store`; Next public routes and sitemap use uncached dynamic fetches. A route-scoped Next proxy checks publication status before the root loading boundary can stream HTTP headers, ensuring unpublished/unknown/suspended sites and disabled optional pages return a real 404. Failed publication checks return 503 without serving cached content. There is no CDN/shared application response cache or invalidation queue in this phase. Every new request resolves the active tenant status and current publication pointer, so unpublishing/suspension cannot serve a stale application cache. Already delivered page/image bytes cannot be revoked from a visitor; open pages refresh within 15 seconds. Availability is recomputed at request time, never cached across schedule boundaries. Do not place a cache/CDN in front of these responses that overrides no-store.

Public JSON contains only the published content snapshot, image descriptions/dimensions and computed operational state; no user, membership, internal restaurant identifier, audit or object-storage fields. Structured content renders through React escaping. JSON-LD escapes `<`. No arbitrary HTML/scripts, invented reviews or ratings are accepted. SEO uses `PUBLIC_ORIGIN` (configure HTTPS for staging), page-specific canonical/title metadata, social images, structured Restaurant identity and a dynamic sitemap. Robots excludes private/setup/auth/API paths. Private preview also sends X-Robots-Tag and no-store.

## Release boundary

Ordering, carts, payment, reservation, POS and delivery workflows are intentionally absent. Phase 3 must use published revision IDs and exact integer configuration pricing, and independently implement transactional order records, taxes, fulfillment fees and payment lifecycle. No Phase 3 launch is implied by this menu configurator.

Production builds explicitly use Next.js webpack, matching the browser test server builder. The original Turbopack builder could not bind its internal process socket in this execution environment.

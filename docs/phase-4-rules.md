# Phase 4 operational invariants

Orders, immutable line/price snapshots, collections and refunds remain the existing commerce records. Operational records link to them. Initial deployment supports the default branch only; every operational request supplies that branch and checks an explicit membership assignment. Existing memberships are backfilled to the default branch. Owner/manager access is not a substitute for branch access.

Advanced features default off. Active pilot ordering entitlement, active tenant/branch, published menu and explicit setup flags are required for new work. Historical work can be resolved after suspension; configuration and new orders cannot. No offline submissions or payments.

Accepted pay-at-pickup orders or settled prepaid orders create station work transactionally. All mapped stations receive distinct work units, each preserving the original ordered quantity without new sales lines. Unmapped items use a fallback station. Work/routing and recipe versions are snapshotted at acceptance. All required work must be ready before the order can become ready. Preparation notes and allergies are separate snapshots. Items cannot be amended; additional table requests create additional orders. Cancellation after preparation is an explicit, reasoned owner/manager action, preserves work, and does not restore consumed stock.

Stock quantities are integer thousandths of the canonical unit (g, ml, each); compatible kg/l inputs convert exactly. No volume/mass conversion. Reserve at acceptance, consume on the first preparation action, release before preparation cancellation. Prepared waste is annotation with zero additional deduction. Tracked items without recipes block acceptance. Available = ledger balance minus active reservations. Manual sold-out remains independent.

Table occupancy derives from active service sessions. Table cleaning is explicit after closure. Walk-ins commit covers until expected departure; seated reservations transfer their allocation to the service session, never count twice. A sweep of overlapping commitments protects aggregate capacity. Session moves/extensions recheck capacity under the restaurant lock. Closure requires all associated orders terminal, no pending refunds, and zero unpaid non-cancelled balances. No table merging or split bills.

Printed QR references are random, hashed, revocable. Staff supply a separate random activation code when opening a visit. Joining issues the existing tenant guest credential plus a hashed, HttpOnly visit capability; printed QR alone cannot read orders. Guest access is limited to their own existing commerce identity. Session closure/revocation blocks further ordering. QR credentials are never analytics/referrer data.

POS uses shared carts, quotes, order submission and payment records, online published availability, original idempotency keys and one tender per order. Counter/takeaway use pickup service mode; dine-in requires a visit. Existing order settlement never creates another order. Browser printing makes no hardware claim.

Cash ledger = opening + cash sales - actually disbursed approved refunds + paid-in - paid-out. Drawer movements and payment/refund updates share a transaction. Restaurant/register/session locks serialize close versus collection; closed sessions cannot change. Duplicate order payment/refund identities cannot repeat drawer effects. Corrections are reasoned paid-in/out entries before close; a closed drawer is immutable.

Delivery is prepaid only (no cash on delivery). Server-selected explicit zone fee, address and instructions are immutable quote snapshots. Only assigned active riders can read necessary address/contact; access ends on reassignment or final state. Ready orders alone may be picked up. Delivery status never implies payment success.

One coupon, no stacking. Eligible item subtotal before discount determines minimum. Fixed/percentage discount is capped by eligible subtotal, distributed deterministically across lines in integer minor units; tax applies after discount, service fees are excluded. Free-delivery only reduces the zone fee. Checkout reserves capacity atomically; acceptance confirms redemption, pending cancellation/expiry releases. Confirmed usage remains consumed after cancellation/refund. Per-customer limits require a verified account. Original discounted line snapshots govern refund ceilings; no historical repricing.

Invitations expire after 48 hours, verified matching identity required, token hash only stored. Resend revokes the original. Managers can grant only a subset of their own permissions and never ownership or staff management. Ownership changes require an active owner and final-owner protection. Authorization is loaded on every API poll; no enduring subscription authorization cache.

Reviews require completed order ownership and are unique per order. Public set = published reviews, including negative ratings. Abuse reports do not automatically hide reviews. Moderation requires an enumerated abuse/privacy/spam reason plus explanation and creates audit history. Internal customer notes never reach public/kitchen/rider responses. Unverified contact values never merge identities.

Exports are background jobs with private database-backed bytes, 24-hour expiry and fresh tenant/branch/action authorization at generation and download. CSV text is formula escaped. PDF uses a minimal local text report renderer, no external provider. Reports keep currencies separate, distinguish completed sales from collections/refunds, cash and stock/waste, and include restaurant/branch/timezone/date filters and generation time. Polling refetches complete authoritative pages after reconnect; actions succeed only on server acknowledgement.

Partial item refunds use the original discounted line amount plus a deterministic allocation of the original tax. Per-unit prefix shares preserve exact totals across partial claims. Locked cumulative quantity claims and the existing collected-minus-reserved refund ceiling prevent duplicate/excess refunds. Fixed service/delivery fees require an explicit amount adjustment or full cancellation policy. Zero owed balances produce no drawer movement.
